# ADR-0006：语言体系设计

- **状态**：已接受
- **日期**：2026-11-19

---

## 背景

平台需要支持多语言。现状问题：

1. **无统一 i18n 框架** —— `scholar-club-new` 中 `i18n` 相关代码 37 处命中，全部各自实现
2. **每模块自建语言表** —— `AgentStore/i18n/texts.ts` 325 行，`Coins` 又一套，`PayConfirmModal` 又是另一套
3. **硬编码中文** —— `pages/Coins/components/PayConfirmModal.tsx` 用 `locale?: 'en' | 'zh'` 局部判断
4. **中英混排** —— `AgentStore/i18n/texts.ts:18` 的描述是中英拼接的单个字符串
5. **切换不彻底** —— `pdf-viewer` README 记录过："语言切换了 但切换之后 实际上 title 啊什么东西都没切换语言呢"
6. **多语言需求分层不清** —— 界面语言（UI）与内容语言（论文摘要/PPT 文字的语言）混为一谈

学术产品的特殊性：论文本身可能是英文，但用户界面是中文；用户可能要用中文界面生成英文 PPT。

---

## 决策

### 1. 区分三类语言

| 维度 | 界面语言 (UI Locale) | 内容语言 (Content Language) | 自定义语言 |
|---|---|---|---|
| 控制什么 | UI 文案、组件文案、日期/数字格式、方向 | 论文摘要、PPT 文字、问答回答 | 与界面语言同机制 |
| 取值 | **12 种内置** + 任意自定义 | **20 种内置** + 任意自定义 | 运行时注册 |
| 谁选 | 用户偏好 / URL / 浏览器 | 生成时指定或自动检测 | 用户 / 机构 |
| 解耦 | ⭐ **界面语言与内容语言完全解耦** | | |

### 2. 界面语言：12 种内置

`zh-CN` `en-US` `zh-TW` `zh-HK` `ja-JP` `ko-KR` `fr-FR` `de-DE` `es-ES` `pt-BR` `ru-RU` `ar-EG`(RTL)

分层：
- **L1 核心**（`zh-CN` / `en-US`）：平台维护，**100% 覆盖**，CI 强制
- **L2 扩展**（其余 10 种）：平台骨架 + 社区补全，**≥80% 覆盖**
- **L3 自定义**：任意 locale，运行时 JSON 注册

### 3. 内容语言：20 种内置 + `auto`

`zh` `en` `ja` `ko` `fr` `de` `es` `pt` `ru` `it` `th` `vi` `id` `ms` `ar` `hi` `fa` + `auto`

比界面语言更广，因为论文与演示面向全球学术读者。

### 4. 回退链（5 级）

```
① overrides[key]          运行时覆盖
② locales[locale][key]    运行时注册（自定义语言）
③ BUILTIN[locale][key]    平台内置
④ BUILTIN['en-US'][key]   英文兜底
⑤ key 本身                永不 undefined
```

**第 4 级兜底英文而非中文**：未配置全的语言用中文兜底会"中英混杂"，用英文至少语言一致。

> 此设计源自 `scholar-pdf-viewer` 的 `resolveMessage()`（已验证），本项目在其基础上**增加命名空间与类型安全**。

### 5. 文案 Key 规范（强制）

```
<domain>.<section>.<element>[.<state>]

common.action.confirm
paper.search.result.count        → "共 {count} 条"
slides.editor.status.rendering
```

- 状态后缀白名单：`error` `loading` `empty` `success` `hint` `tooltip` `label`
- 占位符统一 `{name}`
- key 一经发布**不可重命名**（只能废弃）
- **禁止**代码里写死用户可见文案 → CI 门禁

### 6. 命名空间与类型安全

每个包导出自己的命名空间（`paper.*` `slides.*` …），主站合并。
缺少 key → **编译期报错**（从 `contracts/i18n/messages.schema.json` 生成 `MessageKey` 联合类型）。

### 7. AntD locale 必须联动

```tsx
<ConfigProvider locale={antdLocale}>   {/* 组件文案 */}
  <I18nProvider locale={uiLocale}>    {/* 业务文案 */}
```
两者必须用同一个 locale，否则出现"分页是中文、按钮是英文"。

### 8. RTL 架构预留

- `dir` 由 `LocaleDefinition.dir` 驱动
- Tailwind 用**逻辑属性**（`ms-`/`me-`/`ps-`/`pe-`）
- `ar-EG` 作为 RTL 验证实现
- `slides` 排版引擎的文本量测需支持 RTL

---

## 理由

### 1. 界面与内容必须解耦

| 场景 | UI | 内容 |
|---|---|---|
| 中国研究生读英文论文 | `zh-CN` | `en` |
| 该生做中文组会汇报 | `zh-CN` | `zh` |
| 该生投国际会议 | `zh-CN` | `en` |

**绝不能**用界面语言隐式决定内容语言 —— 否则用户为看英文论文就得切英文界面。

### 2. 12 种界面语言的覆盖依据

- 全球科研产出 TOP 语言
- 华人圈三地（大陆/台湾/香港）
- 一个 RTL 实现做架构验证（阿拉伯语）
- AntD 已内置全部对应 locale（零成本）

### 3. 5 级回退链是唯一可靠方案

前一级可能缺 key（自定义语言必然不全）。必须有确定的兜底顺序，否则会出现 `undefined` 或"中英混杂"。

### 4. 类型安全是必要的

14 个包 × 数百个 key，人工检查不可能。类型 + CI 才能保证。

### 5. 命名空间避免冲突

扁平的 `'load.loading'` 在多包场景会撞（如 `paper.loading` vs `slides.loading`）。命名空间是必需。

---

## 备选方案

### A. 界面与内容共用一套语言

**否决**：用户被迫为读英文论文切英文界面。学术产品不可接受。

### B. 只做中英两种

**否决**：全球学术用户需求；且 RTL 架构需要至少一个验证实现来暴露问题。

### C. 运行时从远程拉取语言包

**否决**：首屏阻塞 + 离线不可用 + 外部依赖。改为**内置 + 运行时 JSON 注册**，远程仅作为可选的补充。

### D. 用 ICU MessageFormat 替代简单占位符

**否决**：复杂。当前需求（`{name}`）简单占位符足够；引入 ICU 会增加包体积与学习成本。**未来若需要复数/性别变体再评估**（i18next 原生支持）。

---

## 后果

### 正面
- 消除 37 处碎片化 i18n 实现
- 切换彻底（CI 保证）
- 界面/内容解耦，用户体验正确
- 自定义语言无需改代码
- 类型安全，缺 key 编译期暴露

### 负面
- **翻译工作量**：L1 需 100% 覆盖所有 key（约 1200+），是持续成本
- **key 命名需要纪律**：命名空间 + 规范 + CI
- **RTL 完整实现延后**：只做架构预留，不做全量阿拉伯语翻译

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 翻译滞后 | L1 由平台维护；L2 允许缺口；CI 只对 L1 强制 100% |
| key 命名不一致 | schema 校验 + CI 门禁 |
| 占位符翻译错位 | CI 校验跨语言占位符集合一致 |
| RTL 后期返工 | M0 就把 `dir` 和逻辑属性写进规范 |
