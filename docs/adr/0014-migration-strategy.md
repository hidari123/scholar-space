# ADR-0014：双轨并行迁移策略

- **状态**：已接受
- **日期**：2026-11-19

---

## 背景

旧系统 `scholar-club-backend` + `scholar-club-new` **在生产运行**，有真实用户、真实数据、真实流量。

新系统是完全重写（13 个子项目）。重写期间必须保证：
1. 旧系统不中断
2. 用户无感知
3. 出问题能快速回退
4. 新系统的质量要能被验证

同时，旧前端已实现 `/api/v2/social/*`（45 端点）、`/api/v2/agent/*`（16 端点）等路径。

---

## 决策

### 1. 双轨并行，逐域灰度

**不做一次性硬切。**

### 2. 网关路径映射 + 特性开关

```
apps/gateway/
├── routing.yaml        # 旧路径 → 新路径 映射表
└── flags.yaml          # 每个域的开关
```

```yaml
routes:
  "/api/v2/agent/flows":     { target: orchestra, flag: orchestra.flows }
  "/api/v2/social/statuses":  { target: community, flag: community.statuses }
  "/api/v2/payment/*":        { target: billing,   flag: billing.all }
  "/api/v2/*":                { target: legacy,     flag: null }
```

**回退 = 关 flag，秒级生效。**

### 3. 切换顺序（按依赖 + 风险）

| 序 | 域 | 风险 |
|---|---|---|
| 1 | core / auth | 🟢 低 |
| 2 | llm / events | 🟢 低 |
| 3 | billing | 🟡 中 |
| 4 | paper | 🟡 中 |
| 5 | slides | 🟡 中 |
| 6 | community | 🔴 高 |
| 7 | orchestra | 🔴 高 |

**先切低风险积累信心，高风险的（community / orchestra）最后切。**

### 4. 数据策略

| 阶段 | 策略 |
|---|---|
| 初期 | **不迁数据** —— 新表独立建，旧表只读 |
| 按需 | ETL 同步（账户、文献库、笔记/高亮）|
| 社区/账单 | **不迁** —— 社区从零（新社区），账单从切换日起新记 |
| 切换后 | 旧库转只读归档，保留 1 年 |

### 5. 鉴权双 token 兼容期

```python
# 先试新 JWT（claims 结构兼容）
# 回退旧 claims（account_id 字段）
```

### 6. 每域有切换检查清单

功能（端点覆盖 / 响应兼容 / 错误码映射 / 分页语义 / SSE 格式）
数据（ETL / 校验 / 双写）
前端（逐项走查 / i18n 迁移 / 各种状态）
观测（错误率 / P95 / 日志 / 埋点）
回退（flag 可关 / 演练通过）

---

## 理由

### 1. 一次性硬切的风险不可接受

新系统是 13 个子项目、约 30 万行代码的重写。任何"应该没问题"的判断在生产前都无法验证。

### 2. 前端零改动是最大的成本优化

如果新后端保持旧路径的响应结构，前端一行不用改 → **验证成本大幅降低**，且随时可回退。

代价是网关要做路径映射 —— 这是很小的成本。

### 3. 逐域切流让每次变更都可验证

一个域一个域切，每次都能：
- 观察真实流量
- 出问题只影响一个域
- 回退只关一个 flag

### 4. 不迁数据（初期）降低复杂度

数据迁移是最容易出不可逆错误的地方。先让新系统独立跑，数据按需同步。

社区与账单**明确不迁**：
- 社区是全新的（模式已变，自研后数据结构不同）
- 账本必须自建（真相源转移要干净）

### 5. 鉴权兼容是必需的

前端持有的 token 格式不变 → 后端换实现时，鉴权必须同时支持两种。这是唯一必须"兼容"而非"替换"的部分。

---

## 备选方案

### A. 一次性硬切

**否决**：风险过高；无回退；无法验证。

### B. 长期双系统并行

**否决**：双轨运维成本高；代码分叉；边界越来越糊。**目标明确：M7 下线旧后端。**

### C. 先改前端再改后端

**否决**：前端重写工作量大，且无法验证后端。若后端先切（前端零改动），收益更大。

### D. 数据一次性全量迁移

**否决**：迁移失败难回滚。先不迁，按需同步。

## 后果

### 正面
- 用户全程无感知
- 每域可独立验证与回退
- 前端零改动 → 验证成本低
- 旧系统可作为对照基准（对比新旧行为）

### 负面
- **网关需要维护路由映射表**（额外的抽象层）
- **迁移期需要双套部署资源**
- **鉴权需要兼容逻辑**（临时复杂度）
- **切换清单的执行成本**（每个域 20+ 检查项）

### 风险与缓解

| 风险 | 等级 | 对策 |
|---|---|---|
| 新旧行为不一致 | 🔴 | 逐端点契约测试 + OpenAPI diff 自动核对覆盖率 + 灰度 1%→10%→50%→100% |
| 鉴权切换失败 | 🔴 | 双 token 兼容期 + 回退开关 + 兼容代码有明确移除节点 |
| 数据迁移丢失 | 🔴 | 双写 + 每日校验 + 可回滚 |
| 旧接口漏迁 | 🔴 | 用 `openapi-diff` 对比旧/新契约，机器发现遗漏 |
| 性能回退 | 🟡 | 压测对比；SSE 替代轮询应显著改善 |
| 团队被迁移工作拖累 | 🟡 | 严格分工：迁移由专人负责；开发轨不被打断 |
| 旧系统迟迟不下线 | 🟡 | **明确 M7 为下线节点**；下线清单写成 checklist |

---

## 下线计划（M7）

```
□ 流量全部切到新服务（观察 2 周无异常）
□ 停止旧后端部署
□ 旧数据库转只读归档（保留 1 年）
□ 旧对象存储文件迁移或保留只读
□ 旧代码仓打 tag 归档
□ 移除鉴权兼容代码
□ 移除网关旧路径映射
□ 更新部署手册与故障预案
```
