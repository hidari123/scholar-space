# ADR-0013：License 合规策略（AGPL 隔离）

- **状态**：已接受
- **日期**：2026-11-19

---

## 背景

本项目的多个参考项目使用强 copyleft 或商业限制性许可：

| 参考项目 | License | 风险 |
|---|---|---|
| `scholarclub-ppt-service`（banana-slides fork）| **AGPL-3.0 + 商业许可条款** | 🔴 闭源商用需向原作者付费 |
| Mastodon（上游）| **AGPL-3.0** | 🔴 同上 |
| `scholar-pdf-viewer` | **MIT** | 🟢 无限制 |
| langflow（上游）| MIT | 🟢 |
| ScholarClaw | 自有 | 🟢 |

产品定位是**闭源商业化**（学术 SaaS，含支付宝计费）。

同时，AGPL 的"网络使用即分发"条款（AGPL §13）意味着：即使只是通过 HTTP 调用一个 AGPL 服务，在某些解释下也可能触发开源义务。**必须从架构上杜绝接触。**

---

## 决策

### 1. 全部自研重写，不拷贝任何 AGPL 源码

**唯一例外**：`scholar-pdf-viewer`（MIT），将来收编。

### 2. 只借鉴"不受版权保护"的要素

| 可借鉴 | 不可借鉴 |
|---|---|
| 数据表字段设计（如 `statuses` 的 `ordered_media_attachment_ids`）| 具体 SQL/Rails 实现代码 |
| REST API 形状（URL 路径、字段名、语义）| 具体处理逻辑代码 |
| 算法思路（如文本量测的方法论）| 具体代码表达 |
| 交互模式与 UX | 视觉素材、图标、文案 |
| 提示词模板（若为原创）| 他人撰写的具体提示词 |

### 3. CI 强制 license 扫描

```
✅ 白名单：MIT / Apache-2.0 / BSD-2 / BSD-3 / ISC / Python-2.0 / PSF
❌ 黑名单：AGPL-3.0 / GPL-3.0 / SSPL / BUSL / Elastic-2.0
```

依赖树中出现黑名单 license → **阻断合并**。

### 4. 架构上隔离外部 AGPL 服务

当前 `scholar-club-backend` 通过 HTTP 调用远程 Mastodon 实例（`mastodon.scholar.club`）。

**决策**：
- 社区功能**完全自研**（`community` + `federation` 包）
- 自研实现**不与 Mastodon 实例通信**
- ActivityPub 协议按规范自行实现（协议本身不受版权保护，实现代码原创）

### 5. 提示词库的处理

`scholarclub-ppt-service/backend/services/prompts.py`（1032 行）来源于 AGPL 项目。

**决策**：
- **不逐字复制**
- 保留其**结构与意图**（大纲生成、页面描述、图像生成、风格提取等）
- 结合学术场景**重新撰写**提示词内容
- 由 LLM 评审逐条对比，确保是独立表达

## 理由

### 1. 商业可行性

AGPL-3.0 的核心条款：作品被使用时必须以 AGPL 方式提供完整源代码。闭源 SaaS 直接违反。

banana-slides 的 README 明确写着：
> 需要商业许可证（Commercial License）（例如：希望闭源使用、私有化部署交付、将本项目集成进闭源产品…），请联系作者

### 2. 纯自研是唯一干净的路

"参考但重写"在法律上比"复制后改造"安全得多。参考对象的**设计思路**不受版权保护，这是软件工程常识。

### 3. 架构隔离比法律论证更可靠

不与 Mastodon 通信 → 不存在"网络使用"关系 → 无论法律如何解释都不触发义务。**这比写法律意见书可靠得多。**

### 4. CI 门禁防止"无意引入"

人会在不知情时 `pip install` 一个 AGPL 包，或复制一段网上的代码。门禁是最后一道防线。

---

## 备选方案

### A. 购买商业许可

**否决**：
- 成本不可控（规模化部署时按用户/实例计费）
- 依赖第三方商业条款（对方停止支持/涨价则无解）
- 与"全面自研"的目标冲突

### B. 保持与 Mastodon 通信（不自研社区）

**否决**：
- AGPL 网络条款的解释风险
- 社区是产品核心（笔记↔论文↔社区联动、arXiv 机器人、AI 审核奖励都是我们的独有资产）
- 无法深度定制

### C. 把整个平台开源（AGPL）

**否决**：与商业化目标冲突。

---

## 后果

### 正面
- 商业闭源无法律障碍
- 社区功能可完全按学术场景设计（不受 Mastodon 数据模型约束）
- 无外部服务依赖（不需要维护 Mastodon 实例）

### 负面
- **社区 + 联邦需从零实现**（约 3-4 周）
- **提示词需重写**（不是复制粘贴）
- **失去 Mastodon 生态的现成能力**（如已有用户、成熟的联邦节点）

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 提示词重写质量下降 | 保留原文件作为**内部对照**，逐条评审独立表达；M3 PoC 验证效果 |
| 社区功能遗漏 | 先做 `COMPATIBLE` 模式对齐 Mastodon API 形状 → 前端零改动切换 → 再补自有能力 |
| 无意引入 AGPL 依赖 | CI license 扫描 + 依赖审查 |
| 联邦实现工作量大 | 独立成 `federation` 包，排到 P2；不阻塞主链路 |
